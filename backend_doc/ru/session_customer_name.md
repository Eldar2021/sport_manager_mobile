# Session — расширение `customerName` (Backend)

> **Цель.** При старте сессии должно быть возможно сохранить **необязательное** имя клиента. Когда клиент возвращается, чтобы закрыть стол, менеджер / владелец сможет найти нужную сессию не только по номеру стола, но и по имени. Имя сохраняется и в завершённых (COMPLETED / CANCELLED) сессиях — в будущем отчётная часть сможет строить аналитику типа «самые частые клиенты».
>
> **Контекст.** Этот документ — **дельта** к [session_api.md](session_api.md): перечисляются только изменения и дополнения. Остальное (жизненный цикл, правило снапшота, аудит `managerId`, error codes, gate подписки) остаётся без изменений.

---

## 1. Модель данных

### БД

В таблицу `sessions` добавляется новая колонка:

| Колонка         | Тип           | Null | Default | Заметки                                                       |
| --------------- | ------------- | :--: | :-----: | ------------------------------------------------------------- |
| `customer_name` | `VARCHAR(80)` |  ✅  | `NULL`  | Сохраняется с trim'ом; пустая строка не сохраняется → `NULL`. |

- **Индекс не нужен** (в v1). Если позже понадобится аналитика «самые частые клиенты», рассмотрим non-unique partial index по `(venue_id, customer_name)` — это отдельное решение для следующей версии.
- **Не уникально.** Одно и то же имя может встречаться сколько угодно раз в одном venue; имя — просто визуальная/поисковая метка, а не система регистрации клиентов.

### JSON-контракт

В обе response-структуры (`SessionLite` и `SessionResult`) добавляется одно новое поле:

```diff
 {
   "id": "...",
   "tableId": "...",
   "managerId": "...",
+  "customerName": "Asan" | null,
   ...
 }
```

- Поле возвращается **всегда** (строка, если задано, иначе `null`). Мобайл не должен проверять наличие через какое-то отдельное поле.
- `SessionLite` (ответы `start` / `pause` / `resume` и embedded session в `venue/selected` / `home`) и `SessionResult` (ответы `finish` / `cancel`, списки в reports) — **все** несут `customerName`.

### Правило снапшота

`customerName` пишется в момент `start` и **не меняется** в течение жизни сессии. На `pause` / `resume` / `finish` / `cancel` менять нельзя — даже если поле прислано, оно **игнорируется**. (Если в будущем понадобится «исправить имя» — это будет отдельный endpoint, в v1 его нет.)

## 2. Изменения эндпоинтов

### `POST /api/v1/session/start`

**Request body — новое опциональное поле:**

```diff
 {
   "tableId": "660e8400-e29b-41d4-a716-446655440001",
+  "customerName": "Asan"
 }
```

**Валидация:**

| Field          | Тип    | Required | Правила                                                                                                                  |
| -------------- | ------ | :------: | ------------------------------------------------------------------------------------------------------------------------ |
| `tableId`      | uuid   |    ✅    | Без изменений                                                                                                            |
| `customerName` | string |    ❌    | После trim — **1-80 символов**. Если после trim пусто → пишется `NULL` (400 не возвращается — чтобы не шуметь клиенту).  |

- Поле **отсутствует** в body или `null` → в БД пишется `NULL`.
- Длина > 80 символов → **`422 INVALID_CUSTOMER_NAME`**.
- Управляющие символы (`\n`, `\t`) при trim приводятся к одному пробелу; не отвергаются.

**Response (201) — `SessionLite`:**

```diff
 {
   "id": "770e8400-...",
   "tableId": "660e8400-...",
   "managerId": "user-101",
+  "customerName": "Asan",
   "status": "ACTIVE",
   ...
 }
```

### Остальные эндпоинты

`pause` / `resume` / `finish` / `cancel`:

- **Body не меняется.** Клиент не отправляет `customerName` в эти эндпоинты; даже если отправит — **игнорируется** (silent ignore). Это защищает от попыток менеджера переписать имя и манипулировать отчётом.
- **В response `customerName` возвращается** (значение, записанное при `start`). PAUSED / ACTIVE / COMPLETED / CANCELLED — без разницы.

### Прочие выдачи (embedded session)

`customerName` также присутствует в:

- `GET /api/v1/venue/selected` → в каждом `table.session`.
- `GET /api/v1/home/...` → в каждой embedded активной сессии.
- Reports — везде, где возвращается список сессий ([reports-api.md](reports-api.md)).

**Эффект на reports (v1):** поле начинает возвращаться; **фильтрация / группировка не реализуются**. Сортировка «самые частые клиенты» явно **отложена на следующие версии**, вне scope v1.

## 3. Error codes

В существующий список добавляется **один** код:

| Code                    | HTTP | Смысл                                                |
| ----------------------- | :--: | ---------------------------------------------------- |
| `INVALID_CUSTOMER_NAME` | 422  | `customerName` превышает 80 символов (после trim).   |

Сообщение готовится на трёх языках (`ru`, `en`, `ky`) — как остальные 4xx, в формате `BaseMessage`. Для пустой строки после trim **ошибка не возвращается**, поле просто становится `NULL` (UX тише).

Остальные error codes не меняются.

## 4. Авторизация

- Для `customerName` дополнительных прав не требуется. `POST /session/start` уже открыт для OWNER и MANAGER; без изменений.
- Subscription gate (`SUBSCRIPTION_REQUIRED`) работает как раньше — новое поле на это не влияет.

---

## 5. Миграция

```sql
ALTER TABLE sessions
  ADD COLUMN customer_name VARCHAR(80) NULL;
```

- Обратная совместимость: все существующие строки получают `NULL`. Для старых сессий имени нет — это ожидаемо.
- **Обратимо** (drop column безопасен, так как в v1 нет активных read-запросов отчётов, использующих это поле).

---

## 6. Logging / Audit

- Считается ли `customerName` в access-логах PII? — **Нет**, имя вводится опционально и с согласия клиента. Тем не менее, body **не дампится** в access-лог; пишутся только status + path. (Поведение и сейчас такое.)
- Если есть webhook'и или audit-очереди на cancel/finish — `customerName` добавляется в payload; PII-фильтр не применяется.

---

## 7. Тест-чек-лист (backend QA)

- [ ] `start` без `customerName` → `customer_name = NULL`, в response — `null`.
- [ ] `start` с `customerName = "  Asan  "` → в БД `"Asan"`, в response — `"Asan"`.
- [ ] `start` с `customerName = ""` или `"   "` → в БД `NULL`, **400/422 не возвращается**.
- [ ] `start` с 81+ символом → `422 INVALID_CUSTOMER_NAME`.
- [ ] В body `pause` / `resume` / `finish` / `cancel` пришёл `customerName` → значение в БД не меняется; в response — то, что было записано при `start`.
- [ ] В embedded session `venue/selected` и `home` поле `customerName` возвращается для каждой сессии.
- [ ] Списки сессий в reports возвращают `customerName`; параметра фильтрации пока нет.

## 8. Открытые вопросы (не делаем в v1)

- [ ] Никакого unique constraint на `customerName` — омонимы (двое разных «Asan») допустимы.
- [ ] Отчёт «самые частые клиенты» — отложен на v2; в v1 только собираем данные.
- [ ] Дополнительные поля клиента (телефон, карта) — вне scope; при необходимости заведём отдельную таблицу `customers`.
